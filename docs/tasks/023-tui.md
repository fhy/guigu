# Task 023: TUI 模式（ratatui 全屏终端 UI）

## Background

015 交付了交互式 REPL（逐行 `tokio::io::stdin`），并明确声明「**TUI（全屏交互界面）不在本任务（属后续）**」。pi 架构本就有独立 `tui(UI)` 层（architecture §1），guigu 缺这一层，交互体验停留在行式 REPL：无流式气泡、无工具进度面板、无滚动历史、无状态栏。

本任务落地全屏 TUI，作为 CLI 的第三种模式（`run` REPL / `acp` / `tui`），复用 022 的模型配置 + 013 `AgentServer` + 015 的装配逻辑（`assemble.rs` 已独立）。TUI 是**纯渲染层**：订阅事件流 + 读快照，不持有 agent 状态，不改 001/003 的「单写者」契约。

## Goal

- 新增 `tui` feature（`ratatui` + `crossterm`，optional）。
- 新增 `guigu tui` 子命令：全屏终端 UI，实时流式渲染对话 + 工具进度 + 状态栏 + 输入框。
- 事件 → UI 状态映射为**纯逻辑**（可单测），终端渲染用 ratatui `TestBackend` 无头验证。

## Design Notes

### 1. 依赖与 feature

```toml
[features]
default = ["providers-http", "config"]   # tui 不在 default（PM 签核：非默认）
tui = ["dep:ratatui", "dep:crossterm"]

[dependencies]
ratatui   = { version = "0.29", optional = true }
crossterm = { version = "0.28", optional = true }
```

- `tui` **非默认（opt-in）**（PM 签核：`guigu tui` 子命令 + 非默认 `tui` feature）。理由：`ratatui`/`crossterm` 依赖树/编译面明显重于 `toml`/`reqwest`，保持 default 精简、降低嵌入方与 `cargo install guigu` 的默认编译负担；需要 TUI 时显式 `--features tui`（或 `cargo install guigu --features tui`）。
- TUI 测试覆盖：default `cargo test` 不编译 `tui` 模块，需以 `cargo test --features tui`（或 `--all-features`）单独跑，验收见下。
- 嵌入方极致 minimal 用 `default-features = false` 剥离（既有先例，021 已文档化）。
- **不引入**：`tui-input`/`tui-textarea`（多行编辑库，minimal 原则，用单行输入 + 历史自实现）、`cursive`（备选框架，不引入，锁定 ratatui）。

### 2. 模块结构（src/bin/guigu/tui.rs，`#[cfg(feature = "tui")]`）

```
tui.rs
├── TuiState               # 渲染所需状态（见 §4）
├── apply_event()          # AgentEvent → TuiState 纯函数映射（§4）
├── handle_key()           # 输入处理：编辑 buffer / 提交 / 退出（纯逻辑）
└── run()                  # 事件循环 + terminal 生命周期（§5）
```

CLI 装配复用 `assemble.rs`（provider 用 022 工厂 + `--config`/`-m` 解析；tools/AgentServer/session 与 015 REPL 完全一致）。

### 3. 布局（ratatui Layout，垂直三区）

```
┌─────────────────────────────────────────────┐
│ 状态栏：模型名 · lane · usage · 运行状态(●idle/◌running) │  ← 1 行
├─────────────────────────────────────────────┤
│ 对话区（可滚动）：user / assistant（流式）/ 工具卡片   │  ← 主体
│   ┌─ tool: bash ───────────────┐            │
│   │ $ ls -la                   │            │
│   │ (输出/进度/结束标记)          │            │
│   └────────────────────────────┘            │
├─────────────────────────────────────────────┤
│ 输入框（单行 + ↑/↓ 历史，Enter 提交）          │  ← 底部
└─────────────────────────────────────────────┘
```

- 宽屏（终端宽度 ≥ 100）可选右侧工具状态面板；窄屏折叠为对话区内联工具卡片。**一期只做内联工具卡片**（单列），右侧面板不实现（声明边界），降低复杂度。

### 4. 事件 → 状态映射（apply_event，纯函数，核心可测点）

`TuiState` 持有：`messages: Vec<Line>`（渲染行）、`streaming: Option<StreamingBubble>`（当前 assistant 增量）、`tool_calls: Vec<ToolCard>`（工具卡片，含状态）、`input: String`、`history: Vec<String>` + 游标、`scroll: usize`、`status: Status`、`usage: Option<Usage>`。

`AgentEvent` 映射（对齐 002/003 事件语义，以实际枚举为准）：

| 事件 | 更新 |
|------|------|
| `MessageStart/Update(Message::User)` | 追加 user 气泡（`>` 前缀或配色） |
| `MessageUpdate` 携带 `AssistantEvent::TextDelta` | `streaming.text += delta`，滚动到底 |
| `AssistantEvent::ThinkingDelta` | `streaming.thinking += delta`（折叠显示「思考中…」） |
| `AssistantEvent::ToolCallStart{id,name,args}` | `tool_calls` 追加 `Running` 卡片 |
| `ToolExecutionStart/Update/End` | 对应卡片状态 → `Running(partial)` / `Done(result)` / `Failed(is_error)` |
| `MessageEnd(Assistant)` / `TurnEnd` | 把 `streaming` 落定成普通 assistant 气泡 + 清空 |
| `AgentEnd` / `AssistantEvent::Error` | `status` → idle/error，落定残留 streaming |

- `apply_event` 为**纯同步函数**，输入 `&mut TuiState` + `&AgentEvent`，无 IO、无锁跨 await——全部可 `#[cfg(test)]` 单测（喂事件序列断言最终渲染行/卡片状态）。

### 5. 事件循环（run）

```
enter alternate screen + raw mode + 隐藏光标
tokio::select! 循环：
  ├─ crossterm::event::poll/read  → 键盘事件 → handle_key（编辑/提交/退出）
  ├─ agent_events.recv()          → apply_event → 触发重绘
  └─ interval tick（100ms）        → 重绘（处理非事件类刷新 + 光标闪烁）
  每次循环后 → terminal.draw(|f| render(f, &state))
退出 → 恢复终端（DisableRawMode/LeaveAlternateScreen/ShowCursor）
```

- 提交 prompt：`server.prompt(session, lane, vec![User])`（复用 013/015），**不阻塞 UI**——事件回环由订阅驱动。
- 键位：`Enter` 提交、`↑/↓` 历史、`Ctrl-C` 首次中止当前 run（`abort()`）、再次 `Ctrl-C` 或 `Esc`/`/quit` 退出、`PageUp/PageDown` 滚动。
- 取消语义：`Ctrl-C` → `server` 的 abort 路径（001/003 定稿的 `abort`），不直接杀进程；退出前 `server.shutdown`。

### 6. 测试策略

1. **纯逻辑单测（`#[cfg(test)]`，无终端）**：`apply_event` 逐事件断言（text delta 累积、tool 卡片状态机 Running→Done/Failed、streaming 落定、AgentEnd 置 idle）；`handle_key`（Enter/↑↓/Ctrl-C/Esc 的状态迁移）。
2. **渲染无头测试（ratatui `TestBackend`）**：`render` 输出到 `Terminal::new(TestBackend)`，断言 buffer 含预期文本（状态栏模型名、user 气泡、工具卡片标题）。
3. **CLI 冒烟（tests/cli.rs）**：`guigu tui --help` 打印且退出码 0；`guigu tui` 在无 TTY 环境下应报清晰错误而非 panic（raw mode 失败 → `ProviderConfigError`/`CliError` 风格错误 + stderr）。
- 测试不依赖真实 TTY/外网（fake/offline provider 冒烟，对齐 015 策略）。

### 7. 边界声明（明确不做）

- **多行编辑框 / 富文本 / 语法高亮**：单行输入 + 历史，不引入 `tui-textarea`。
- **右侧工具面板 / 分屏多 lane 视图**：一期单列内联卡片。
- **鼠标交互 / 复制粘贴选择**：仅键盘。
- **TUI 作为独立库模块**（`src/tui` 对外可嵌入）：一期放 `src/bin/guigu/tui.rs`（CLI 专属），不提升为库级模块（避免膨胀公开 API 面）。
- **跨平台终端兼容性极致处理**（Windows 旧 console）：crossterm 已抽象，不做额外降级。
